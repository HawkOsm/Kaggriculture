## 2026-08-21 — train_rl.py: found and fixed a real PPO replay-buffer staleness regression during the 8h unattended GPU run
- Command: unattended `python train_rl.py --hours 8 --resume` (RTX 4070 Laptop), monitored via `training_log.csv` every 30 min across several hours and two prior restarts (see gen 1-175).
- Result: `eval_margin` (deterministic policy vs. champion) degraded steadily once the 12,000-episode replay buffer filled — from a best of -4604.8 (gen 125) down to -9229.9 (gen 161), while `mean_margin` on the same stale-mixed batch stayed flat/noisy, masking the regression until dedicated eval checks caught it. Root cause: with `--replay-episodes 12000` and ~200 new episodes/generation, episodes sat in the buffer for ~60 generations (2.5h+) before aging out, so most of every PPO update was importance-sampled against `old_log_probs` from a policy dozens of generations stale — breaking the near-on-policy assumption the clipped surrogate objective depends on.
- Notes: fixed in `src/train_rl.py` — `--replay-episodes` dropped 12000 -> 2000 (~10 generations turnover, ~25-30min lag), `--max-ppo-epochs` 15 -> 8 and `--target-kl` 0.08 -> 0.04 (now feasible again on the smaller buffer without re-triggering the earlier "stuck at epoch 1" problem), and added an elite-retention safeguard: 3 consecutive evals landing >1500 below `best_margin` now auto-reverts the live network+optimizer to `best.pt` and clears the replay buffer, so an unattended run can't keep drifting away from its own best result for hours undetected. Repaired the live checkpoint by hand once (model weights from `best.pt` gen 125, fresh Adam optimizer state, emptied replay buffer, generation counter kept continuous at 175) and relaunched; confirmed clean resume in the log. Known, accepted tradeoff: the smaller buffer means less GPU work per update, so `gpu_util_avg` will likely sit below the originally-requested 65-75% target — correctness of the learning signal took priority over hitting that band. Also built `Kaggriculture_RL_Colab.ipynb` (self-contained, embeds all source via `%%writefile` since the repo is private) to optionally run training on Google Colab in parallel; flagged in the notebook itself that Colab's free-tier ~2 vCPUs will likely bottleneck the CPU-bound rollout collection harder than this machine's 22 cores, so it's additive throughput, not a guaranteed speedup, unless run on a higher-CPU Colab Pro/Pro+ runtime.

## 2026-08-20 — robust_agent.py: scaling-strategy redesign from reverse-engineered #1 player data + submission rebuild
- Command: ad hoc Python match runs (`run_match.py`-equivalent) at each iteration, then `python src/optimize.py --n-trials 80 --n-jobs 8 --opponents melon_maxxer,multi_crop,champion` (see entry below this one for that run's own numbers), then `python src/build_submission.py` + ad hoc verification loading `submission/main.py` by file path.

- Notes: reverse-engineered the leaderboard #1 player (Ryo Hasegawa)'s strategy from two public replays -- aggressive day-0 hiring ramping to 8-12 hands/day, fast land expansion (all quadrants by day ~10), a large pasture-only (no coop) animal operation, near-zero cash tolerance, and a MELON+WHEAT -> STRAWBERRY -> WHEAT crop-phase rotation -- and initially just copied those numbers directly into `DEFAULT_CONFIG` (`max_hires_per_day: 12`, `pasture_target_ratio: 1.0`, immediate land/animal spending). That version was badly broken in three distinct, sequential ways, each real and worth remembering: (1) day-0 cash crash -- hiring/land/animals all competing for the same thin starting pile with no dedicated floor for the (very cheap) hire cost, fixed by giving HIRE its own `hire_money_floor` separate from the general `money_reserve`, and a separate `animal_reserve_multiple` for the much pricier animal purchases; (2) reward is money *at game end*, not cumulative -- continuing to hire/build/buy land in the final days (no time to pay back) and leaving shed inventory unsold was pure waste, fixed with an explicit `wind_down_days` liquidation phase (force-sell everything, stop all new spending) plus a `season_days` cutoff so crops that can't mature before the season ends never get planted; (3) **land bought faster than the crew could physically reach and tend it** -- at `max_hires_per_day: 12` with land bought on pure affordability, ~half of all unlocked tiles sat permanently empty (confirmed by direct tile-count inspection: 46-63 empty tiles out of 75-100 unlocked, and *growing* over time) because our simple greedy-nearest-tile unit dispatcher spends most turns walking a wide board rather than working it -- confirmed via action-type histogram (76% movement vs ~24% actual harvest/water/plant/etc). This is a genuine limit of the current routing, not something more tuning fixes: blindly copying a top player's raw scale numbers without matching their (unknown, presumably more sophisticated) unit routing actively lost to a modest single-hand baseline in local head-to-head testing. Backed off to a moderate scale (`max_hires_per_day` ~5-7, `land_utilization_threshold` restored to a real gate ~0.5-0.7 instead of pure affordability) and handed the rest to `optimize.py`'s Optuna search rather than continuing to hand-guess -- that search's own promoted config (see below) landed on `max_hires_per_day: 7`, `land_utilization_threshold: 0.60`, `pasture_target_ratio: 0.45`, validating the moderate-scale hypothesis with a real verified result instead of a guess. Also added `src/build_submission.py` (AST-based, extracts the relevant functions from `farm_utils.py`/`robust_agent.py` + bakes in `best_config.json`) so `submission/main.py` is generated instead of hand-maintained -- this caught one real bug immediately (`import math` was missing from the generated file, since `_plan_units` now uses `math.ceil` but the old hand-copy predated that code and the generator's first draft forgot it) before it could have reached a real submission.
